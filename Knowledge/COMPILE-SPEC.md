# PDF 到 Wiki 编译规范（PDF-to-Wiki Compilation Specification）

编译把已审核 Raw 证据变成人类可读、可互链、可持续修订的知识。它不是复制摘要。

## 发布门

仅当 `extraction-report.md` 明确标记 `status: approved` 时开始正式编译。端到端测试可以生成 draft 页面，但必须保留 `evidence_status: needs-review`，不得冒充已审核知识。

## 编译步骤

### 1. 建立上下文

读取：

1. `Knowledge/Wiki/index.md` 与 `overview.md`。
2. 强制术语注册表。
3. Raw 的 `manifest.json`、`source.md`、图表、表格、公式和报告。
4. 与标题、材料名、方法名、缩写和别名匹配的现有 Wiki 全文。

### 2. 分流（Triage）

- `New`：产生新的来源页或知识页。
- `Update`：给已有知识页增加证据或限定条件。
- `Disputed`：新证据与已有结论冲突。
- `No material`：没有带来可复用知识，只保留来源记录和日志。

状态可以组合，但 `No material` 与其他状态互斥。

### 3. 先建来源页

每份主文和 SI 各建一个 `Sources/` 页面，记录：研究问题、主要结论、体系、方法、关键参数、图表索引、限制、与伴随文档的关系。来源页忠实于单篇文档，不做跨论文综合。

### 4. 提取可复用知识单元

逐条判断内容的中心对象，并路由到十一类目录。只有满足下列至少一项才建独立页：

- 会被多个项目复用。
- 已有两个及以上来源共同讨论。
- 是理解核心结论不可缺少的体系、现象、模型、方法或可观测量。
- 存在值得持续追踪的争议或开放问题。

否则保留在来源页，避免 Wiki 过度碎片化。

### 5. 合并而不是追加摘要

更新已有页时：

- 将新证据并入对应论点，而不是在底部再贴一份论文摘要。
- 明确说明新来源是支持、限定、反驳还是提供方法。
- 保留旧结论及其历史状态。
- 只在全局认识发生变化时更新 `overview.md`。

### 6. 生成变更计划

写入前展示：

```text
Create: 新页面
Update: 已有页面及修改章节
Conflict: 冲突主张与双方证据
Supersede: 拟废弃但保留的内容
No material: 不进入 Wiki 的内容
```

获得人类确认后才写入。

### 7. 级联检查

发布后全文搜索受影响的材料、现象、模型、方法、缩写和主张。更新真正受影响的页面关系，但禁止无意义地给每页增加大量链接。

### 8. 验证与日志

依次运行：

1. `health`：frontmatter、稳定 ID、路径、索引、日志和断链。
2. `lint`：证据缺失、冲突、过期结论、孤页、稀疏页和知识空白。
3. 人工抽查页面的快速阅读区、图表和关键主张。

日志格式：

```markdown
## [YYYY-MM-DD] compile | 页面标题
- Sources: source-id
- Disposition: New | Update | Disputed | No material
- Created: [[页面]]
- Updated: [[页面]]
- Human approval: pending | approved
```

## 查询反哺

普通查询只在对话中回答。只有用户明确要求保存时，才把具有长期价值的综合写回最相关知识页或 `Projects/` 页面；先展示证据和变更计划，不自动创建“聊天记录页”。

## 知识变好的机制

知识库通过四个闭环演化：

1. **摄入闭环**：新来源补充或挑战旧主张。
2. **查询闭环**：真实问题暴露页面难读、缺证据或缺连接的位置。
3. **审核闭环**：人类纠正物理解释、术语和重要性排序，并锁定关键判断。
4. **维护闭环**：health 保结构，lint 保语义，Git 保历史。

目标不是页面数量，而是让可靠主张、适用边界和科研问题之间的连接持续变清晰。
